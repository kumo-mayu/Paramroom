## 0. 結論

1. **当初の目的（VRC+ のコレクションの容量の制約から逃れる）は、VRChat の仕様上成り立たない** [ユーザー確認]。
   - Print を作るには、ゲーム内で撮った写真でも Gallery（64 枚）を通る。Gallery が満杯なら、どの方法でも Print を作れない。
   - Gallery に上げた画像をそのまま Print に変える道も、今は使えなかった。
   - そのため、「カメラジャックで撮れば Gallery を使わずに済む」という前提が崩れた。以下は、仕様の理解と今後の似た研究のために完成させた記録である。
2. **画像を自分のアバターに送って写真に写す仕組み自体は、実機で動いた** [実測]。
   - 768×512〜960×960 の画像が **0.4〜2.3 秒で揃い**、60〜120 ms で復号された。
   - カメラジャックで撮った 4K の写真では、**元画像との色の差が平均 0.4 以下**で、文字も等倍で読めた。
3. **経路**：PC の送信道具 → OSC → **同期しない Float パラメータ** → FX の Direct ブレンドツリー → マテリアル → カメラループの RenderTexture。
   - 同期しないので、他の人には何も届かない。この経路は Paramroom の同期（256 bit・100 ms）とは別物で、制約もまったく違う。
4. **経路の実力**（K = パラメータの数）【実測】：
   - **Float 1 個で 30 bit を誤りなく運べる**。
   - **1 フレームに入るのは最後に届いた 1 送信分だけ**。
   - **K=512 で最高 1.35 Mbit/s**、K=1024 で 1.64 Mbit/s。1024 では送信中の fps が 57 まで落ちる。
   - Animator の負荷が K の 2 乗で増えるので、**K=512 前後が釣り合いのよい点**。
5. **符号化は JPEG 系の DCT（4:4:4・標準ハフマン表）を採用した**。
   - ブロック圧縮の 1/2.3〜1/2.7、生の画素の 1/7〜1/10 のビット数で済む（報告 12）。
   - シェーダーでの復号は、参照実装と画素単位で一致した（差は最大 1）。
6. **今の Paramroom の方式（楕円の図形、256 bit 同期）は、この用途には向かない**。
   - 最終画質に上限がある（MS-SSIM 0.99 に届かない画像がある）。
   - 途中参加・取りこぼしへの強さという長所が、この用途では要らない。

## 1. 目的と、制約がどう変わったか

**目的（依頼）**：Prints でローカルに表示できている画像を、Paramroom を介してリモートの人にも見せる。VRC+ の Collection の容量の制約から、実質的に解放されることを狙った。

**構成（利用者の案）**：

1. PC の画像を**自分のアバターだけ**に送る
2. カメラジャックのシェーダーで、VRChat の写真カメラに写る絵を差し替える
3. 撮った写真を Print にする。Print は VRChat のサーバーを通して配られるので、リモートの人にも見える

これでリモートの人に届けるのは Print の仕組みになり、Paramroom がするのは「自分のクライアントまで画像を運ぶ」ことだけになる。従来の制約は次のように変わる。

| 従来の制約 | この用途では |
|---|---|
| 同期パラメータ 256 bit | **同期しないパラメータ**（個数の上限 8192）。ただし予算は利用者が決めた（最大 4000 bit 程度、のちに「個数で数え、実際に動いた数を上限にする」） |
| 同期は約 100 ms ごと | **1 フレームごと**（自分のクライアントの fps） |
| 途中参加者にも絵を成立させる | **不要**（見るのは自分だけ） |
| 取りこぼし・順不同 | 残る（フレームをまたいだ半端な反映）。ただし率は低く、再送で埋まる |
| 評価 | **完成までの時間が最優先**。途中の見え方は副次 |

## 2. 確認された制約

### 2.1 パラメータと OSC [公式・コミュ]（エージェントの一次資料調査、2026-09-19）

- 「8000 前後」の正体は **8192 個**（ビットではない）。「VRChat also limits your avatar to 8192 total custom Expression Parameters (synced and unsynced)」[公式 https://creators.vrchat.com/avatars/animator-parameters/ ]。2024.2.1 で「local/non-synced total」8192 になった [公式]。
- 同期しないパラメータはクランプされない：「unsynced parameters are unaffected by these limits」[公式 2023.1.2p3]。
- OSC で書いた Float はローカルで 32 bit のまま：「When updated locally, such as with OSC, float values are stored as native (32-bit) floating-point values」[公式]。
- Animator にしか無いパラメータは OSC で書けない（issue #2 が Open のまま）[コミュ]。**Expression Parameters に載せて Synced を外す**必要がある。
- OSC の受信回数・バンドルを一度に適用するか・データグラムの大きさの上限は、**公式に記載なし** [公式を探して無し]。
- 同期の枠（256 bit）と周期は、2025〜2026 年のリリースノート約 70 本で変わっていない [公式]。
- パラメータの数による負荷：「Parameters on the local avatar seem to cost 1.5 ms per 1000」[コミュ実測、測り方不明]。→ §5.1 で原因を切り分けた。

### 2.2 Prints・Gallery [公式・公式wiki・コミュ・ユーザー確認]

- Print は **VRC+ が作れる**。「All prints will always upload in 1080p」。保存枠は VRC+ で 64 枚、ワールドに出せるのは 1 人 9 枚 [公式wiki https://wiki.vrchat.com/wiki/Prints ]。
- 見る側は「フレンドのみ」「非表示」を選べる。インスタンス・ワールドの設定で Print を無効にできる [公式 help・2025.1.3]。
- Photo Gallery は **VRC+ のクラウドの画像置き場（64 枚）**。ゲーム内でローカルの写真フォルダを一覧する機能は見つからない [公式wiki・未確認]。
- **Gallery に上げた画像を Print にする道は、現状できない。ゲーム内で撮った写真も Gallery を通るので、Gallery が満杯だと Print を作れない** [ユーザー確認、2026-09-19]。
- 非公式 API（`POST /prints`）で直接上げるツールがある [コミュ]。ただし「upload content ... on a user's behalf」を禁じる Creator Guidelines に触れうる [公式]。**候補から外した**。
- シェーダーから写真カメラを見分ける：`_VRChatCameraMode`（0 通常、1 VR の手持ちカメラ、2 デスクトップの手持ちカメラ、3 スクリーンショット）[公式 https://creators.vrchat.com/worlds/udon/vrc-graphics/vrchat-shader-globals/ ]。カメラジャックを規制したという情報は無い [未確認]。

### 2.3 実機・Unity で確かめた制約 [実測]

条件：メイン機、デスクトップモード、fps 上限なし、静かなワールド（ホーム）、利用者のアバター＋測定用プレハブ（`measure/unity/Assets/ParamroomLocalProbe`）。

| 項目 | 結果 | 根拠 |
|---|---|---|
| OSC で同期しない Float に書けるか | **書ける** | 全測定で「正しい」チャンク数 = 届いた数 |
| 1 個で運べるビット | **30 bit**（2^23 を足して非正規化数・NaN を避ける）。Unity では任意の正のビット列（31 bit）が Direct ブレンドツリーを通った。負の値は 0 になる | プローブの試験、Unity の LocalBits |
| 1 データグラムの上限 | **3.4 KB は通り、5.1 KB は捨てられる**（受信のバッファ 4 KB と推測） | 大きさを変えた送信 |
| 1 フレームに入る量 | **最後に届いた 1 送信分だけ**。fps を超えて送った分は上書きで消える（60 fps で 90 送信/秒 → 67%、120 → 50%） | 送る速さを変えた送信 |
| バンドルの原子性 | 1 バンドル（32 個）でも 2 フレームに分かれて反映されることがある | 組ごとの印で検出（捨てた組 0.4〜5%） |
| 負荷の中身 | **OSC の受信・解析はほぼ無料**。重いのは「値が 0 でない」状態の維持（K=512 で約 2.3 ms）と値の変化 | 無いアドレス／同じ値／変わる値に送り分けた（§5.1） |
| Animator の負荷と K | **K の 2 乗で増える**。1 本の Direct ツリーで 1 レンダラーだと 500:1.0 ms、1000:3.6、2000:14.0、4000:54.6、8000:216（Unity エディタ）。入れ子・レイヤー分割・Transform でも 2 乗のまま。32 個ずつ別レンダラーで半分 | Unity LocalFeasibility・LocalScaling |
| 重み 0 のレイヤー | 動かさなくても**プロパティがあるだけで負荷がかかる**（2048 個で 1.7 ms） | Unity LocalLayers |
| OSC での着替え | **VRChat の起動後にアップロードしたアバターには着替えられない**（「Trying to change to an inaccessible avatar」）。起動前からあるものは着替えられた | VRChat のログ |
| 長時間 | 3 分間の連続送信（毎秒 75 送信）で誤り 0、fps 94〜97 で安定 | §5.1 |

## 3. 比べた方式

報告 12 で 17 方式を比べた（16 枚、元の解像度、閾値に届くビット数）。要点だけ再掲する。

| 方式 | MS-SSIM 0.99 に要る bpp | 受信側の処理 | 判定 |
|---|---:|---|---|
| **DCT（JPEG 系）4:4:4** | **0.75** | ブロック位置 → 係数 → 逆 DCT（数パス） | **採用** |
| DCT 4:2:0 | 0.75 | 同上＋色差の拡大 | 写真ではわずかに有利、文字で不利 |
| ウェーブレット 9/7 | 0.78 | 逆変換 10 パス前後、長い可変長 | PSNR・文字で 15〜35 % 少ないが重い。次の候補 |
| BC1 相当（＋縮小） | 2.03 | ほぼ不要 | 実装が最も楽な予備 |
| パレット | 3.15（15/16） | 表引き | 不採用 |
| 差分予測（DPCM） | 3.00 | 行ごとの逐次 | 不採用 |
| 生画素 RGB565 / 888 | 5.87 / 7.65 | 不要 | 不採用（7〜10 倍） |
| 楕円 primitive（現行） | 0.74（11/16 のみ） | 図形数に比例 | 最終画質に上限、不採用 |

**「大量の同期しないパラメータで運ぶ」という構成そのもの**も比べた（依頼の手順 5）。

- **公式サイト → Gallery → Print**：アバターを使わない、より単純な道。今は使えない [ユーザー確認]。
- **非公式 API で Print を直接上げる**：規約の懸念で除外。
- **アバターから画像を読み込む手段**：無い [公式を探して無し]。

## 4. 実装（研究用）

### 4.1 転送層（プローブと共通）

- パラメータ `PRL0..PRL{K-1}`（Float、同期しない、保存しない）。32 個で 1 組、組ごとに別のレンダラー（Animator の負荷が半分になる）。
- 値は `float のビット = 2^23 + v`、`v = [印 2][中身 28]`。印は送信回数 mod 4。
  - 1 組の中で印がそろっていなければ、その組は捨てる（フレームをまたいだ半端な反映）。
  - 組は独立していて、先頭の 1 個が見出し（チャンク番号）。残り 31 個 × 28 bit = **1 チャンク 868 bit**。
- **1 組 = 1 OSC バンドル = 1 データグラム**（約 1.3 KB。4 KB を超えると捨てられるため）。
- 受信側（カメラループ）：組ごとのクアッドが、頂点シェーダーで 32 個の値を検査し、チャンクの 32 テクセルの上に移動して書く。取りこぼしても遅くなるだけで壊れない（順序非依存・冪等）。

### 4.2 画像の形式 lpic v1（`sim/local/lpic.js`）

- YCbCr 4:4:4（JFIF）、8×8 DCT。量子化表は品質から計算し（libjpeg の整数の式）、送らない。
- JPEG 標準のハフマン表（Annex K）を使い、表は送らない。画像ごとに表を作る場合より数 % 多くなるが、kodim23 では品質 50 で 0.77 bpp・MS-SSIM 0.9905 で、見積もり（0.75 bpp）とほぼ同じ [実測]。
- チャンク 0 が見出し（幅・高さ・品質・チャンク数）。ほかのチャンクは「最初のブロック番号 20 bit・ブロック数 8 bit ＋ 840 bit の符号」。
  - ブロックはチャンクをまたがず、DC の予測もチャンクで切る。**どのチャンクも単独で読める**。
- 符号化は 0.15〜0.3 秒（node、1 スレッド、〜960 px）[実測]。

### 4.3 受信側（`measure/unity/Assets/ParamroomLocalImage`）

カメラ 5 台で、同じフレームの中で順に処理する。

1. **置き場 A**：写し＋組の書き込み
2. **置き場 B**：写し＋統計。全チャンクが揃ったかを見出しのチャンク数で判定する
3. **ブロック位置**：ブロックごとに、どのチャンクの何ビット目から始まるかと DC の絶対値。二分探索＋チャンクの頭から読む
4. **縦の逆 DCT**：128 行の帯ごと。各テクセルが自分の 3 ブロックを読んで、列 u の 8 係数を拾う
5. **横の逆 DCT ＋色変換**：1024×1024 の画像へ

- **揃ってから 1 回だけ**（念のため 2 周）、1 フレームに 1 帯ずつ走らせる。それ以外のフレームは、頂点シェーダーでクアッドを消して何もしない（RenderTexture が絵を保つ）。
- RenderTexture は約 8 MB（1024² の画像 4 MB、帯 2 MB、ブロック位置 0.8 MB、置き場 2 × 0.5 MB）。
- **カメラジャック**：`_VRChatCameraMode != 0` のとき画面全体を画像にし、縦横比を保って黒い帯を付ける。sRGB → 線形に戻して出す。写真の向きは `_ProjectionParams.x` で合わせる。
- HUD：統計（白黒のマス目）と縮小表示。通常のカメラのときだけ出し、鏡と写真には出さない。着ている本人にだけ出る。
- 送信道具：`measure/osc/local-image.js`（符号化して送る、ジャックの切り替え）。読み取り：`local-probe-read.js --image`（PrintWindow で窓が重なっていても撮れる）。

## 5. 測定結果

### 5.1 転送層（プローブ）[実測]

**パラメータ数 K ごと**（fps 上限なし。最高の実効 = 送信/秒 × 組数 × 868 bit × 1 周目の到達率）：

| K | 止めているとき | 値を保つだけ | 最高の実効（送信/秒、送信中の fps） |
|---:|---:|---:|---|
| 128 | 179 fps | 169 fps | 0.50 Mbit/s（150、148 fps） |
| 512 | 168 | 122 | **1.35 Mbit/s**（100、97 fps） |
| 1024 | 142 | 76 | 1.64 Mbit/s（60、57 fps） |
| 2048 | —（着替えられず未測定） | | |

**負荷の切り分け**（K=512、毎秒 30 / 60 送信）：

| 送るもの | 30 送信/秒 | 60 送信/秒 |
|---|---:|---:|
| （止めている） | 171 fps | |
| アバターに無いアドレス（受信・解析だけ） | 171 | 170 |
| 同じ値を送り続ける | 122 | 123 |
| 毎回変わる値 | 112 | 102 |

- 値を保つ負荷（2.3 ms）は送る速さによらない。Direct ツリーが重み 0 の子を省いているためと見られる [推測]。
- 変化の分（30 送信で +0.7 ms、60 で +1.6 ms）は速さにほぼ比例する。VRChat が変わった値を OSC で送り返すことも一因と見ている [推測・未確認]。
- **送り終わったら全部 0 に戻せば、負荷は消える**。

### 5.2 Unity での受信側の検証 [実測: `ParamroomLocalImageTest`]

- kodim23（768×512、品質 50）と mahara（960×847、品質 75）：
  - **シェーダーの復号と参照の復号の差は最大 1**。1 を超える画素は 0（39 万画素・81 万画素）。
- 1 チャンク欠けていれば復号しない。最後の 1 つで同じ絵に復号される。
- カメラジャック（1920×1080 の写真を模した描画）：上下の向きが正しく、色は、参照を同じく双線形補間した値との差が 0。
- 試験が効くかも確かめた：DC の積み上げを外すと差 181 で落ちた。プローブでは、印の検査を外すと半端な組が書き込まれて落ちた。

### 5.3 VRChat での画像の転送 [実測: K=512、毎秒 90 送信・2 周]

| 画像 | 品質 | 大きさ | チャンク（bpp） | 揃うまで | 復号 | 最長フレーム |
|---|---:|---|---|---:|---:|---:|
| kodim23（写真） | 50 | 768×512 | 347（0.77） | **0.42 秒** | 68 ms | 16 ms |
| kodim23 | 75 | 768×512 | 528（1.17） | 0.58 | 66 | 12 |
| kodim23 | 92 | 768×512 | 1118（2.47） | 1.31 | 66 | 20 |
| kodim05（細かい写真） | 85 | 768×512 | 1637（3.61） | 2.25 | 62 | 18 |
| mahara（文字） | 75 | 960×847 | 1282（1.37） | 1.56 | 100 | 19 |
| mahara | 90 | 960×847 | 2191（2.34） | 2.24 | 99 | 18 |
| イラスト（顔） | 85 | 960×960 | 1254（1.18） | 1.50 | 123 | 18 |
| イラスト（年賀） | 85 | 960×571 | 1389（2.20） | 1.61 | 79 | 18 |

- 「揃うまで」は最初のチャンクから最後のチャンクまで。符号化（0.15〜0.3 秒）と、送る前の待ち（0.3 秒）は含まない。
- 送信中 88〜92 fps、表示し終えて待機中 141 fps（K=512 の画像プレハブ）。

**1 周目で届かなかったチャンク**（mahara 品質 90、2191 チャンク、1 周だけ、各 2 回）：

| 送信/秒 | 1 周の時間 | 届かなかった数 |
|---:|---:|---:|
| 45 | 3.02 秒 | 0、0 |
| 60 | 2.27 | 3、0 |
| 75 | 1.81 | 9、5 |
| 90 | 1.51 | 52、50 |
| 105 | 1.30 | 461、462 |

- **1 回の送信が 2 フレーム以上映る速さ（送信中の fps の半分ほど）なら、半端に反映されたフレームの次のフレームで正しく取れるので、1 周で揃う**。
- 速く送ると、取りこぼしを 2 周目で待つ時間が増える。今の送り方（毎秒 90・2 周）は、1 周目の約 1.5 倍かかっている。

### 5.4 写真（カメラジャック）[実測: 4K 写真 1 枚、ホームのワールド]

- mahara 品質 90 を送り、ジャックを有効にして、利用者がデスクトップのカメラで撮った（3840×2160）。
- 写真の中の画像の位置は、シェーダーが置いた位置と画素単位で一致した（x 696〜3143）。
- 写ったのは画像だけで、ワールドも HUD も写らなかった。
- **色の平均のずれ**：参照の復号に対して RGB で −0.08 / −0.08 / −0.07、元画像に対して −0.33 / −0.27 / −0.40。**ワールドのポストプロセスによる色の変化は見えなかった**（このワールドでは）。
- 元の大きさに縮め直して比べると、参照に対して MS-SSIM 0.995、PSNR 30.3 dB。PSNR が低いのは、2.55 倍に拡大（双線形補間）して箱型フィルタで縮め直したことによるもので、写真側の劣化ではない。文字は 4K 写真の等倍で読める。
- 道具：`measure/analysis/jack-compare.js`。

## 6. 採用方式とその理由

**K=512、組 = 1 データグラム、lpic v1（DCT 4:4:4・標準ハフマン表）、揃ってから帯ごとに復号、カメラジャック。**

- **K=512**：
  - 128 → 512 で速さは 2.7 倍、待機 fps は 179 → 168（−6%）。
  - 512 → 1024 では速さは 1.2 倍にしかならず、送信中の fps は 97 → 57 に落ちる。Animator の負荷が 2 乗だからで、「増やしても伸びが小さくなる点」がここにある。
- **DCT**：
  - 必要なビット数が最少級（報告 12）。
  - 受信側は、チャンクごとに独立して読める形にすれば 3 パスで済み、参照と画素単位で一致させられた。
  - ウェーブレットは 1 割ほど少ないが、受信側がずっと重い。
- **揃ってから復号**：
  - 評価の最優先が完成までの時間なので、途中の表示は捨てた。
  - そうすれば復号は 1 回（60〜120 ms）だけで済み、それ以外のフレームは負荷がかからない。
- **送る速さ**：
  - 1 周で確実に揃えたいなら、送信中の fps の半分ほど（K=512 で毎秒 45 前後）。
  - 速く送る場合は 2 周。どちらも差は 1 秒以内。

## 7. 既存の Paramroom 方式との差

| | 既存（同期・楕円 primitive） | 今回（ローカル・DCT） |
|---|---|---|
| 届く相手 | 他の人（フレンド・Show Avatar、PC） | 自分だけ（他の人には Print として届ける想定だった） |
| パラメータ | 同期 Int 最大 32 個（256 bit） | 同期しない Float 512 個（同期 0 bit） |
| 更新 | 約 100 ms ごと | 1 フレームごと |
| 速さ | 256 bit / 100 ms = 2.56 kbit/s（上限） | 約 1,000 kbit/s（**約 400 倍**） |
| 完成まで | 80 秒ほどでほぼ揃う（形式 4 ＋ 32 Int） | **0.4〜2.3 秒**（〜960 px） |
| 最終画質 | 512 px 相当の図形近似 | 元の解像度の JPEG 相当（品質 50〜92） |
| 途中の見え方 | 数秒で分かる絵（強み） | 揃うまで出さない |
| 途中参加・取りこぼし | 強い（強み） | 不要（自分だけ）。取りこぼしは再送で埋める |
| 負荷 | 軽い | 送信中は fps が大きく下がる（168 → 90 前後）。待機は軽い |
| VRAM | 約 4 MB（形式 3） | 約 8 MB |

**線の上の形式や既存のプレハブには一切触れていない**。パラメータ名も別（`PRL*` など）。

## 8. 実装案（もし製品にするなら）

前提（目的）が崩れたので、**今は製品にする予定はない**。

同じ仕組みが生きるとしたら、次のような場面だと考える [推測]。

- 自分の視点で画像を確かめる
- 配信・録画に画像を載せる
- 手持ちカメラの写真に画像を焼き込む

そういう用途が出てきたときの案は次のとおり。

1. **送信アプリ**（`Paramroom.App`）に「ローカル画像」モードを足す。
   - `lpic.js` を C# に移し、参照とビット単位で一致させる（`sim/local/lpic.js` が参照）。
   - 送り終えたら全パラメータを 0 に戻す。
2. **ビルダー**に K=512 のプレハブを加える（`ParamroomLocalImageBuilder`）。
   - 形式番号の仕組み（`Paramroom_Format`）とは別の名前空間にし、既存の形式と混ぜない。
3. **取りこぼしの再送を賢くする**。送信側が HUD（または小さな受信済み地図）を PrintWindow で読み、届いていないチャンクだけ送り直す。
   - mahara 品質 90 なら 2.24 → 約 1.6 秒になる見込み [推測]。
   - ただし、VR では画面の位置が変わる、HUD が画面に出る、など扱いにくい。
4. 大きな画像（1024 px 超）や 4:2:0 の切り替え、画像ごとのハフマン表は、必要になってから。

## 9. 残っている不確実性（未検証）

- **VR モード**：fps・写真カメラ（`_VRChatCameraMode = 1`）・HUD の位置。すべてデスクトップでしか測っていない。
- **別の PC**：負荷（値を保つ 2.3 ms、変化 1 個あたり約 5 µs）は CPU によって変わる。サブ PC では未測定。
- **K=2048**：着替えられず未測定。1024 までの傾向から、速さは頭打ち、fps は大きく下がると見る [推測]。
- **Print そのもの**：実際に Print にしたときの画質（1080p の枠、表示時の BC7／ASTC 圧縮）と、リモートからの見え方。Gallery の制約が分かったので撮っていない。
- **ポストプロセスの強いワールド**：色がどれだけ変わるか。今回はホームのワールドだけで測った。
- **「値の変化」の負荷の中身**：OSC の送り返しが原因かは確かめていない。
- **プローブ無しのアバターの fps**：HUD が無いと読めないので、K=128・512・1024 から外挿した値（約 180 fps）しかない。
- **1 周目の取りこぼしの内訳**：半端な反映と上書き（fps 超え）の割合は分けていない。
- **起動後にアップロードしたアバターへの OSC での着替え**：なぜ inaccessible になるか（再起動で直るか）は確かめていない。

## 10. 再現方法

```bash
# 符号化と参照の復号

Unity -batchmode -projectPath <p> -executeMethod ParamroomLocalImageTest.Run -imageOut <dir> -imageData mahara-q75

# VRChat（プレハブ入りのアバターを着て、OSC を有効に。デスクトップ）
node measure/osc/local-probe.js run --k 512 --chunks 2048 --rate 75 --passes 2

node measure/osc/local-image.js jack 1        # 写真カメラに画像を写す（撮り終えたら 0）
node measure/analysis/jack-compare.js <photo.png> <expected.png> [<original.png>]
```
