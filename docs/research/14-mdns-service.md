# 調査報告 14: mDNS の名乗り（着替えると別のポートにつながる件）

調査日: 2026-09-20。メイン PC（[docs/measure/environment.md](../measure/environment.md)）。
道具: `measure/osc/mdns-watch.js`（mDNS を**受信だけ**して、名前とポートの変化を出す）。

## 凡例

**[実測]** この調査で測った / **[ログ]** VRChat の output_log の記録 / **[推測]** 推論・未検証

---

## 0. 結論

1. **利用者の報告（実機でアバターを切り替えると接続が切れ、別のポートでつながる）は、v0.2.2 より前の
   送信アプリの挙動で再現した** [実測]。**今の版（v0.2.2 と `main`）では再現しない**。
   - 09-18 のビルド（修正前）：**13 秒ごとに新しいポートで名乗り直す**
   - v0.2.2 の公開 exe と `main` のビルド：90 秒動かして**名乗りは 1 回だけ**、ポートは変わらない
2. **ただし、別の欠陥が見つかった**：アプリと CLI が**同じ名前**（`Paramroom-Sender`）で名乗るので、
   両方動いていると**mDNS の登録が互いに上書きし合う**（改名は起きない）[実測]。
   VRChat がどちらのポートを覚えるかは運任せで、片方が終了すると死んだポートに `/avatar/change` を送り続ける。
3. **直した**（`main`）：
   - 名乗る名前にプロセス ID を入れる（`Paramroom-Sender-<pid>`）
   - **CLI は名乗らない**（探すだけの作りにする。`new VrcConnection(advertise: false)`）

---

## 1. 症状と、ログに残っていたもの

利用者の報告：「実機でアバターを切り替えたときに接続が切れて別のポートでつながることがある。何度か再現した」。

VRChat のログ（2026-09-19 22:25 起動のセッション）に、**同じ名前・別のポート**が 12 回出ていた [ログ]。

```
23:15:41 Found new OSC Service: Paramroom-Sender at 127.0.0.1:64885
00:05:42 Found new OSC Service: Paramroom-Sender at 127.0.0.1:63558
00:05:55 Found new OSC Service: Paramroom-Sender at 127.0.0.1:63586
00:06:07 Found new OSC Service: Paramroom-Sender at 127.0.0.1:51888
   …（00:08:31, 00:11:13, 00:27:48, 00:37:41, 00:37:54, 00:55:17, 00:57:40, 01:00:03）
```

- **どれも着替えの 1〜5 秒後**に出ている（`kipkip01`（Paramroom なし）と `light256`（Paramroom あり）の往復）。
- 13 秒しか空いていない組がある。手で起動し直したにしては短い。
- 同じ日の 16:08 のセッション（こちらの測定のみ。送信アプリは起動していない）には 1 件も無い [ログ]。

## 2. 再現 [実測]

`mdns-watch.js` で受信だけして、送信アプリを 90 秒動かした。

| 動かしたもの | 名乗った回数 | ポート |
|---|---|---|
| `bin/Release` にあった 2026-09-18 18:51 のビルド（修正前） | **7 回（13 秒ごと）** | 毎回変わる |
| v0.2.2 の公開 exe（GitHub の Releases から取得） | 1 回 | 変わらない |
| `main` のビルド（今回の修正前） | 1 回 | 変わらない |

- 13 秒は「見回り 10 秒 ＋ 探索の待ち 3 秒」に一致する。修正前は**探すたびにサービスを作り直していた**（v0.2.1 までの作り）。
- 接続を 1 つだけ作って探索を 6 回繰り返す小さなプログラムでも、ポートは変わらなかった。
  **ライブラリ（VRChat.OSCQuery 0.0.7）の `RefreshServices()` は名乗り直さない** [実測]。
- VRChat は着替えのときに OSC サービスの一覧を取り直すと見られる。だから「着替えの直後」に新しいポートが記録される [推測]。

**したがって、利用者が動かしていたのは修正前のビルドだった可能性が高い** [推測]。
`bin/Release` には 09-18 のビルドが残っていた（`dotnet build` は古い出力を消さない。CLAUDE.md の注意どおり）。
公開版 v0.2.2 を使っていた場合は別の原因になるので、どの exe を起動していたかは確かめる必要がある。

## 3. 同じ名前で名乗ると奪い合う [実測]

アプリを 2 つ（と CLI を）同時に動かすと、`Paramroom-Sender` の SRV 記録が交互に書き換わった。

```
PORT CHANGED Paramroom-Sender._osc._udp -> 51789 (was 54478)
PORT CHANGED Paramroom-Sender._osc._udp -> 54478 (was 51789)   … 1 秒おきに交互
```

- mDNS の名前衝突の解決（改名）は起きなかった。**どちらの答えが後に届いたかで、ポートが決まる**。
- VRChat が古い方を覚えた状態でそのプロセスが終わると、`/avatar/change` は届かなくなる。
  アプリは 10 秒ごとの読み直しで拾うので致命的ではないが、**着替えが即座に反映されなくなる**。
- CLI は 1 回の実行ごとに一時的なサービスを作っていたので、`paramroom list` を打つだけでこれが起きた。

## 4. 直したこと（`main`）

| 直した点 | 中身 |
|---|---|
| 名前を一意に | `Paramroom-Sender-<プロセス ID>`。アプリを 2 つ起動しても奪い合わない |
| CLI は名乗らない | `new VrcConnection(advertise: false)`。`OSCQueryServiceBuilder().WithDiscovery(...)` だけで作る |

**確かめたこと** [実測]：

- 直した版のアプリ：名乗りは 1 回（`Paramroom-Sender-28096`）、ポートは変わらない。
- 直した版の CLI：`list` を 2 回実行しても、mDNS に**何も出ない**。
- 名乗らない作りでも、他のサービス（`OyasumiVR`、アプリ自身）を見つけられる。
- `dotnet test` 76 件が通る。

## 5. 未検証

- **利用者が昨夜動かしていた exe がどれか**（公開版 v0.2.2 か、`bin/Release` に残っていた 09-18 のビルドか）。
- **VRChat の中での確認**。今回の再現と修正の確認は、VRChat を起動せずに mDNS だけで行った。
  着替えを含む実機での確認（名乗り直しが起きないこと、着替えが数秒で反映されること）は、これから。
- VRChat が着替えのときに OSC サービスの一覧を取り直すかどうか（ログの並びからの推測）。
- 名前にプロセス ID を入れたことで、VRChat 側に「終了したアプリの登録」が増える。実害は見ていない [推測]。
