# 調査報告 04: 関連プロジェクト VRChat-OSC-Video の分析と現行検討方式との比較

調査日: 2026-09-17
対象: https://github.com/vFeez/VRChat-OSC-Video （2025-06 作成、最終 push 2025-10-04、Python、ライセンス表記なし、★11）
凡例: [事実: ソース] リポジトリのコード/README で確認 / [実測] 本リポジトリの sim で再現可能 / [推測]

方針: 既存実装があること自体は採用理由にしない。各設計要素を同じ評価基盤で測り、利点・欠点を個別に判断する。

---

## 1. 方式の要点 [事実: ソース]

- 用途: **Webカメラのライブ映像**を自分のアバターに表示（README「VERY low resolution (16x14) live video」）。
- 画像: 16×14 に縮小（INTER_AREA）、R/G/B 各チャネルを `value // 64` で **2bit** に量子化（ディザなし）。
- パラメータ: `webcam_pixel/{row}_{col}` の **int 28 個**（7 行 × 4 byte、1 byte = 2bit × 4 画素）。
- 1 パケット = **1 色チャネル × インタレース片フィールド**（偶数行 or 奇数行の 7 行）。
- ヘッダ: bool `RG`・`B`（2 つでチャネル選択。グレースケール版は両方 1）、bool `interlacing_flag`、float `Ratio`（縦横比 − 1）。合計 **224 + 3 + 8 ≈ 235 bit**。
- 送信: 各パケットの後に `time.sleep(0.11)`。OSC は **31 メッセージを逐次送信**（非原子的）。連番・CRC・再送制御・ack なし。
- 周期: カラー 1 フレーム = 6 パケット（README「~1.5FPS」）、モノクロ = 2 パケット（「~5fps」）。
- 受信側: 公開アバター `avtr_c8a3370f-…` があるが、アバター（Animator/シェーダー）はリポジトリに含まれず、**受信側のバッファ実装は未確認**。16×14×3ch×2bit = 1344 bit を保持する必要があるので、Animator のローカルパラメータかカメラ RT のどちらかと推測。
- **リモートでの実測値（届くフレームレート・欠落率）の記載はない**。0.11 秒という保持時間にも根拠の記載はない。

## 2. 同じ評価基盤での比較 [実測]

静止画向けに一般化した `sim/codecs/raw.js` を実装（1 パケット＝固定数の生画素値、ID は周期長に応じた最小ビット幅、`rows2` がオリジナル相当の行インタレース）。チャネル `bm14`（保持 0.14 秒、取得間隔 100〜180ms 一様、欠落約 7%）、MS-SSIM（YCbCr 6:1:1）。

| 画像 / B | 方式 | 1s | 2s | 5s | 10s | 20s | 60s |
|---|---|---:|---:|---:|---:|---:|---:|
| kodim23 / 256 | **raw g16-b2-rows2（元方式相当, 7 パケット周期）** | **0.704** | 0.704 | 0.704 | 0.704 | 0.704 | 0.704 |
| | raw g32-b3-lattice | 0.553 | 0.648 | 0.816 | 0.862 | 0.862 | 0.862 |
| | wavl L48-12 | 0.695 | 0.800 | 0.888 | 0.915 | 0.931 | 0.988 |
| | prim t7-r128-n1000 | 0.741 | 0.811 | 0.890 | 0.927 | 0.952 | 0.973 |
| illust_tux / 256 | raw g16-b2-rows2 | 0.751 | 0.751 | 0.751 | 0.751 | 0.751 | 0.751 |
| | wavl L48-12 | 0.757 | 0.849 | 0.916 | 0.944 | 0.953 | 0.996 |
| | prim | 0.847 | 0.900 | 0.954 | 0.974 | 0.983 | 0.992 |
| kodim23 / 32 | raw g16-b2-rows2（64 パケット周期） | 0.351 | 0.393 | **0.593** | 0.688 | 0.704 | 0.704 |
| | wavl L192-64-20 | 0.386 | 0.473 | 0.584 | 0.705 | 0.789 | 0.852 |
| | prim e6.5.4-r256-n200 | 0.444 | 0.498 | 0.651 | 0.725 | 0.789 | 0.866 |

- 256bit では、元方式相当の raw は **1 秒で wavl と同等の画質に達し、以後は伸びない**（16×16・各色 2bit が上限）。
- 画質が頭打ちになる代わりに、**周期が約 1 秒と極端に短いため、欠落や途中参加から 1 秒で回復する**（途中参加の比較は評価実行中）。
- 32bit では周期が 9 秒に伸び、序盤の優位はほぼ消える。
- 最終画質・中盤の画質は wavl / prim が大きく上回る。

## 3. 使える知見・見落としていた設計

### 3.1 【重要】極短周期のサムネイル常時再送（二重ストリーム構成）[実測＋推測]
- 現行案は「重要度順に並べた 1 本の長い周回（30〜90 秒）」で、途中参加者は周回の途中から始まる。既に実測で、重要度順の方式は途中参加で大きく崩れる（例: 256bit・周回 90 秒で wavl の AUC 0.866→0.434）。
- 元方式は正反対の設計で、**画像全体を約 1 秒周期で送り続ける**ので、いつ参加しても 1 秒で粗い全体像が出る。
- **見落としていた設計**: 「数秒周期のサムネイル専用ストリーム」と「長周期の詳細ストリーム」をスロットで多重化する二重構成。サムネイル側は周期が短いので ID ビットも少なくて済む（§3.2）。現行の `tier` スケジュール（先頭の重要ユニットを繰り返す）は近い発想で、評価中。二重構成を明示的な方式として実装・比較する価値がある。

### 3.2 周期長に応じた短い ID・可変長 ID [推測・要検証]
- 元方式のヘッダは 3bit（6 パケット周期）。現行方式は ID/アドレスに 8〜17bit を使い、32bit 予算では 1/3〜1/2 を占める。
- 案: 重要な先頭ユニットには短い ID（例: `0`＋4bit で先頭 16 ユニット）、それ以外は `1`＋長い ID。先頭 16 ユニットは 1 パケットあたり 4〜6bit 節約でき、序盤画質に効く。代償は後続ユニットの 1bit 増。32/64bit で特に効く可能性。

### 3.3 画像メタデータ（縦横比など）[事実: ソース → 現行設計の欠落]
- 元方式は `Ratio` で縦横比を送る。**現行のシミュレーションは 256×256 の正方形しか扱っておらず、縦横比・解像度・画像 ID を送る設計が抜けている**。ヘッダユニット（高優先・周期再送）に入れる必要がある。

### 3.4 デコーダの単純さを評価軸に明示する [推測]
- 元方式の受信側は「値をラッチして表示するだけ」で、シェーダー実装リスクが最小。現行上位の prim（画素ごとに数百〜千図形のループ）、wavl/pw（可変長復号＋逆ウェーブレット多段）は実装と負荷のリスクが高い。
- 比較表に「シェーダー実装難度・フレーム負荷」を画質と並べて載せ、最終推奨に反映する。

### 3.5 動く内容（映像・更新）への対応範囲 [要判断]
- 元方式はライブ映像。現行案は静止画を前提にしている。スライドショーや描き足しのような「更新」を扱うなら、エポック 2bit だけでは不足し、差分更新の設計が要る。**用途の範囲はユーザー判断事項**。

## 4. 採用しない（または根拠にしない）要素とその理由

| 要素 | 判断 | 理由 |
|---|---|---|
| 0.11 秒の保持時間 | 根拠にしない | 実測の記載がない。映像なら欠落が次フレームで上書きされるので問題が表面化しないが、静止画の累積伝送では欠落率が直接画質に効く。値は 03 報告書の実機測定で決める |
| 非原子的な逐次 OSC 送信を許容 | 静止画では不可 | 映像は次フレームで上書きされる。静止画の累積伝送では半端パケットが残留しうる（既に実測で確認済み、CRC か再受信での上書き修復が必要） |
| RGB チャネル別パケット・一様 2bit 量子化 | 画質面では不利 | 同じ 256bit で、raw の最終値 0.704 に対し wavl は 1 秒で同等、5 秒で 0.888。色の冗長性（YCbCr・色差の間引き）と量子化の工夫が効いていない |
| 行インタレース | 同等以下 | 32×32 で行インタレースと 2 次元格子順は最終値が同じ。途中の見え方は格子順が有利と推測 |
