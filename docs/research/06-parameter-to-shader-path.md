# 調査報告 06: Expression Parameters からシェーダーへ値を渡す経路と、シミュレーション前提の妥当性

調査日: 2026-09-17
凡例: [公式] VRChat/Unity 公式資料・スタッフ発言 / [コミュ] 非公式 / [推測] / [未確認] / [実測] 本リポジトリの sim。✔ = メイン agent が原文を確認。

## 0. 結論

1. **シェーダーから Expression Parameters を直接読む手段は無い**。アバターのシェーダーに公開されている VRChat グローバルはカメラ・ミラー・時刻系のみ [公式]。パラメータをシェーダーに渡す機能のリリースノート記載も見当たらない。
2. **Animator のアニメーションでマテリアルプロパティを書き換える経路が公式に使える**。FX レイヤーでは「material swaps, shader animations」を含めて全てリモートにも反映される [公式✔ playable-layers]。
3. **Bool に分解する必要はない**。同期パラメータを **Int（8bit）** にし、Animator コントローラ側では同名パラメータを **Float 型**で宣言すると、VRChat が「Directly converted to float（1 → 1.0）」で変換する [公式✔ animator-parameters の型不一致変換表]。これを Direct ブレンドツリーの重みにして、`material._Pi = 1` の 1 キークリップを掛ければ、プロパティ値 = 0〜255 の整数（float32 で厳密）になる [推測: 算術上]。シェーダー側は `round(_Pi)` で 8bit を得る。
4. **Float パラメータにビットを詰めるのは不可**: リモートでは k/127（255 段階、128 に相当する符号が無い）、送信者ローカルは 32bit float のまま、Puppet 操作時は補間される [公式✔]。
5. **シミュレーションの抽象化（decoder が各スナップショットの B bit をそのまま受け取る）は、Int パラメータ＋Direct ブレンドツリー経路で成立する見込み**。B = 256/128/64/32 はそれぞれ Int 32/16/8/4 個で、8 の倍数なのでちょうど合う。ただし資料だけでは確定できない点（§4）があり、実機検証が必要。
6. **既存の研究結果への影響は小さい**。方式の順位や傾向を変える要素は見つからなかった。新たに次の設計ルールが必要になった: **(a) 全ゼロなど「過渡的な偽パケット」を無効として扱う**（§3.2 で一部方式に影響を確認）、**(b) 送信側 OSC の非 atomic 書き込み対策**（既にモデル化済み）、**(c) 空きビットが 8 の倍数でない場合は端数を Bool で使う**。

## 1. 推奨経路（案）

| 段階 | 設定 | 根拠 |
|---|---|---|
| Expression Parameters | `D0…D(n-1)`（n = B/8）を **Int・Synced**、メニューには出さない | Int は補間されない、Puppet で IK 同期に切り替わらない [公式から推測] |
| FX コントローラのパラメータ | 同名で **Float 型**として宣言 | 型不一致変換「int → float: Directly converted」[公式✔] |
| FX レイヤー | 常時有効な 1 ステート、Motion = **Direct ブレンドツリー**（Write Defaults **ON**、Normalized Blend Values **OFF**）。子: クリップ `Set_Pi`（`material._Pi` を定数 1 の 1 キー）×重み `Di` | Direct ツリーは子の重みにパラメータを直接使う [公式: Unity Manual]、VRChat では WD ON 必須・正規化オフ [コミュ: vrc.school] |
| レンダラー | デコーダ専用のメッシュ。`_P0…` の既定値 0 | アニメーションは同じレンダラーの全マテリアルスロットに効く [コミュ: Canny] |
| シェーダー | `uint b = (uint)round(_Pi);` から B bit を組み立てる | KAT が同様に `round(_CharN)` を使用 [コミュ] |

- 代替: 1 つのプロパティに複数 Int を合成（子クリップの定数を 1, 256, 65536）すると 24bit までは float32 で厳密 [推測]。プロパティ数を減らしたい場合のみ。
- 1D ブレンドツリー（しきい値 0 と 255）でも可能だが、Direct ツリーの方が単純で誤差が小さい [推測]。
- 既存例: KillFrenzy Avatar Text は 128 個の float プロパティを 1 レンダラーで駆動し、`round` で復元（1D ツリー、WD OFF）[コミュ]。

## 2. 公式・コミュニティ資料の要点

- シェーダーグローバル: `_VRChatCameraMode`, `_VRChatMirrorMode`, `_VRChatTimeNetworkMs` 等のみ。「Do not use the `_VRChat` prefix…」[公式] https://creators.vrchat.com/worlds/udon/vrc-graphics/vrchat-shader-globals/
- FX レイヤー: 「in the FX layer, everything is copied over! … material swaps, shader animations, particle system animating」[公式✔] https://creators.vrchat.com/avatars/playable-layers/
- 型不一致変換表（int→float 直接変換、float→int は Mathf.Round、bool→float は 1.0/0.0）[公式✔] https://creators.vrchat.com/avatars/animator-parameters/
- アニメーションによるマテリアルプロパティ変更は MaterialPropertyBlock 経由（Unity フォーラムのユーザー回答、スタッフではない）[コミュ]。単一のデコーダメッシュなら描画コスト上の問題は小さい [推測]。
- Direct ブレンドツリー: WD ON 必須、正規化オフ、「初回進入時に 1 フレームだけ値が 0 になりうる」[コミュ: vrc.school]。
- 同期: カスタムパラメータは Playable sync「0.1 to 1 seconds as needed」、IK sync は float を補間 [公式✔、01 報告書]。
- 送信側 OSC: バックグラウンドスレッドで受信し「次のフレーム更新でメインスレッドに適用」[コミュ: vrchat-community/osc]。32 個の Int を順に送ると、同期スナップショットが書き込み途中を拾う可能性 [推測]。
- リモートの Animator カリング: 「When culled, animators do not run.」（Tupper）、ただし「距離や表示数で明示的に非表示にしたときのみ」（Dexvoid）[公式スタッフ、発言間で範囲の記述に差]。
- 代替経路（ブレンドシェイプ、ボーン位置、パーティクル等）は精度・カリング・容量のいずれも劣る [コミュ/推測]。

## 3. シミュレーション前提への影響

### 3.1 前提が成立する部分
- **ビットの厳密性**: Int → Float（直接変換）→ Direct ツリー（重み×1）→ `round`。float32 は 2^24 まで整数を厳密に表せるので 0〜255 は厳密 [推測: 算術]。→ sim の「B bit を正確に受け取る」は成立する見込み。
- **パケット長**: 256/128/64/32bit は Int 32/16/8/4 個に一致。
- **半端パケットのモデル**: sim は「先頭 j バイトが新パケット、残りが旧パケット」で破損を作っており、これは **Int パラメータ単位の非 atomic 更新**と同じ粒度 [推測]。前提と整合。
- **カリングによる停止**: sim の `cull` バースト（受信停止→再開時は最新値から）と整合。

### 3.2 新たに見つかった前提の穴: 過渡的な偽パケット
- ブレンドツリー初回進入時の「1 フレームだけ 0」[コミュ] や、アバター読み込み直後の初期値（全パラメータ 0）が、**有効なパケットとして decoder に取り込まれる可能性**がある [推測]。
- 全ゼロのパケットを復号済み状態に 1 回適用し、その後 1 周期分を正しく再送したときの影響 [実測: `sim/review/zero-packet.js`、kodim23、MS-SSIM(色差込み)]:

| 方式 | 復号完了時 | 全ゼロ適用後 | 1 周再送後 |
|---|---:|---:|---:|
| wavl 256 | 0.9916 | 0.9916（影響なし） | 0.9916 |
| dctv 256 | 0.9417 | 0.9417（影響なし） | 0.9417 |
| pw 256 | 0.9897 | **0.7438** | 0.9897 |
| prim 256 | 0.9754 | **0.8813** | 0.9754 |
| pal 256 | 0.8497 | **0.2015** | 0.8497 |
| raw 256 | 0.7045 | **0.5642** | 0.7045 |
| wavl 32 | 0.9845 | 0.9845 | 0.9845 |
| prim 32 | 0.8928 | **0.7597** | 0.8928 |

- 可変長符号の方式（wavl, dctv）は、全ゼロではパディング規則により何も書き込まれず影響なし。ユニット ID ＋固定長の方式（prim, pw の図形部, pal, raw）は「ID 0 のユニット」を全ゼロで上書きして大きく劣化し、正しいユニット 0 の再受信まで残る。
- **対策（設計ルールとして追加）**: エポック値 0 を「無効」に予約する（全ゼロパケットを捨てる）、または CRC。コストは 0〜数 bit。既存の順位評価には含まれていない劣化要因だが、対策が安価なので結論は変わらない見込み [推測]。

### 3.3 資料だけでは判断できない点（実機検証が必要）
1. **スナップショット内の全パラメータが同じフレームで Animator に反映されるか**（反映がフレームをまたぐと受信側でも半端パケットが生じる）。
2. **Playable sync の実際の送信タイミング**（「0.1〜1 秒 as needed」の実態、保持時間との関係）→ 03 報告書の測定計画と同じ。
3. **受信側で Int → Float → ブレンドツリー → プロパティの値が厳密に整数になるか**（0/255/0x55/0xAA/歩行ビット/乱数）。
4. **初回進入時・読み込み時の過渡値**の発生有無と持続フレーム数。
5. **カメラループのカメラ自体が「可視」扱いになり、カリングを防ぐか**。
6. 32〜128 個のプロパティをアニメーションさせるフレーム負荷。

## 4. 検証方法（03 報告書の測定セットアップに追加）

| # | 検証 | 方法 | 合否 |
|---|---|---|---|
| V1 | 値の厳密性 | OSC で既知パターンを全 Int に書き込み、シェーダーで `abs(_Pi - round(_Pi))` を拡大表示、`round(_Pi) == 期待値` を色で表示。送信者ローカル、リモート、ミラーで確認 | 全パターンで誤差 0 |
| V2 | 同一フレーム反映 | D0 と D(n-1) を同じ OSC バーストで変更し、RT ループのフレームカウンタで両者の変化フレームを記録 | 常に同じフレーム |
| V3 | 半端パケット率 | CRC 付きパケットを保持時間 H を変えて送信し、リモートで CRC 不一致の割合を記録 | sim の torn 率仮説（5%）を実測値に置換 |
| V4 | 過渡値 | アバター再読み込み・途中参加・表示/非表示の切替直後に、全ゼロや既定値パケットが観測されるか記録 | 発生頻度と持続フレーム |
| V5 | カリング | 後ろを向く、距離/表示数で非表示、ミラー越しのみ、で RT 更新の停止と再開を記録 | cull バーストモデルの置換 |
| V6 | 負荷 | 32 / 128 プロパティ、1 レイヤー Direct ツリーでのフレーム時間 | 許容範囲か |

## 5. 既存研究結果の扱い
- 02 設計報告の方式比較・順位は、本調査の範囲では**そのまま有効**（前提の中核である「8bit Int × n 個を厳密に受け取れる」が公式仕様の組み合わせで成立する見込みのため）。
- ただし全方式に「エポック 0 無効化（全ゼロ拒否）」を設計要件として追加する。固定長 ID 系（prim, pw, pal, raw）で特に必要。
- 実機検証 V1〜V4 のいずれかが不成立の場合（特に V2 の同一フレーム反映）、受信側でも半端パケットが生じるため、CRC を必須化し sim の torn 率を引き上げて再評価する。
