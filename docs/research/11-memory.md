# 調査報告 11: メモリを減らせるか

調査日: 2026-09-18
きっかけ: 「メモリ消費を抑えたりは可能ですか」。アバター側（VRAM）と送信アプリ側（PC の RAM）の
両方を測った。

## 凡例（証拠タグ）

- **[実測]** 測った値 / **[推測]** そこからの推論

## 0. 結論

| どこ | いま | 減らせる先 | どうやって |
|---|---:|---:|---|
| **アバター（形式 3）** | **8.38 MB** | **4.19 MB** | アトラスを ARGBHalf から ARGB32 にする |
| アバター（形式 6・1024px） | 32.63 MB | 16.31 MB | 同上 |
| アバター（QR 専用） | 0.06 MB | — | すでに十分小さい |
| **送信アプリ（4000x3000 の写真）** | **471 MB** | **150 MB 前後** | 元画像を double 配列で丸ごと持たない |
| 送信アプリ（960px の画像） | 150 MB | 100 MB 前後 | 作業用の配列を float にする |

**アバター側は ARGB32 にするだけで半分になる。** これが一番効く。

## 1. アバター側（VRAM）[実測: 計算]

デコーダーは**アトラスを 2 枚**持つ（カメラループは読みながら書けないので、交互に使う）。
テクセルは ARGBHalf = 8 バイト。

| 形式 | アトラス 1 枚 | 合計（2 枚） | うちキャンバス | うち置き場・制御 |
|---|---|---:|---:|---:|
| 3 / 4 | 1024x536 | **8.38 MB** | 8.00 MB | 0.38 MB |
| 5 | 1024x538 | 8.41 MB | 8.00 MB | 0.41 MB |
| 6 | 2048x1044 | 32.63 MB | 32.00 MB | 0.63 MB |
| 10（QR 専用） | 64x58 | 0.06 MB | — | — |

**95% がキャンバス**（描き直し中の作業用と、表示中の完成版の 2 面）。置き場と制御行は誤差。

### 案 A: ARGBHalf → ARGB32（**勧める**）

8 バイト/テクセルが 4 バイトになるので**ちょうど半分**。

置き場に入るのは 0..255 のバイトで、8 bit なら**そのまま正確に入る**（丸め無し）。
制御行の値も全部 255 以下。問題はキャンバスで、**バッチごとに 8 bit に丸められる**こと。

誤差を見積もった [実測: 2 万回の試行]。最悪の想定として「図形 1 個ごとに丸める」でも:

| | |
|---|---:|
| 最終的な誤差の平均 | **0.25 階調**（0..255） |
| 途中も含めた最大誤差 | **1.75 階調** |

**α 合成は前の誤差を (1-α) 倍に減らすので、誤差は溜まらない。** 表示はどのみち 8 bit なので、
見た目に影響しない [推測]。実装したら Unity の試験（期待値との maxdiff）で確かめられる。

### 案 B: 作業用キャンバスをやめる

キャンバスが 1 面になるのでさらに半分。ただし**描き直しの途中が見えてしまう**
（粗い絵 → 細かい絵、を 1 秒ほどかけて繰り返す）。**採らない。**

### 案 C: 制御行の前後の余白を詰める

いまは高さに 16 行の余裕がある（制御行は +8 の 1 行だけ使う）。15 行削れば 0.23 MB。
**ついでにやる価値はあるが、それだけでは効かない。**

## 2. 送信アプリ側（PC の RAM）[実測: ピーク作業セット]

| 画像 | ピーク |
|---|---:|
| 960x640（kodim23） | 150 MB |
| 960x1200（スクリーンショット） | 150 MB |
| **4000x3000（写真）** | **471 MB** |

原因は 2 つ [推測]:

- **元画像を `double[]` で丸ごと持っている**（1 画素 24 バイト）。4000x3000 なら 288 MB。
  形式を変えたときに作り直せるよう、縮める前の画像を保持している
- **符号化の作業用配列**（512x512 の RGB を double で数本、16 スレッド）が 150 MB の土台

減らし方:

1. **読み込みの時点で縮める**。デコードした 8 bit のバイト列から直接 512（または 1024）へ
   縮めれば、288 MB の double 配列を作らずに済む。**ただし縮小の計算順が変わるので、
   出力が今と 1 bit も同じではなくなる**（JS の参照実装との突き合わせが効かなくなる）
2. **保持する元画像を「長辺 2048 まで」に落とす**。1 と違って計算順は変わらない。
   4000x3000 なら 288 MB → 75 MB
3. **作業用配列を `float` にする**。土台が半分になるが、符号化の結果が変わる

**1 と 3 は出力が変わるので、突き合わせの仕組みを作り直す覚悟が要る。2 は変わらない。**

## 3. 未検証

  テクスチャ容量に入るなら、8.38 MB → 4.19 MB はランクにも効く
- 送信アプリのピークが 150 MB を下回れるか（.NET のランタイム自体の下限がある）
