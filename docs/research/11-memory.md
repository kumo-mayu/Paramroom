# 調査報告 11: メモリを減らせるか

調査日: 2026-09-18
きっかけ: 「メモリ消費を抑えたりは可能ですか」。アバター側（VRAM）と送信アプリ側（PC の RAM）の
両方を測った。

## 凡例（証拠タグ）

- **[実測]** 測った値 / **[推測]** そこからの推論

## 0. 結論

| どこ | いま | 減らせる先 | どうやって |
|---|---:|---:|---|
| **アバター（形式 3）** | **8.38 MB** | **4.19 MB** | アトラスを ARGBHalf から ARGB32 にする |
| アバター（形式 6・1024px） | 32.63 MB | 16.31 MB | 同上 |
| アバター（QR 専用） | 0.06 MB | — | すでに十分小さい |
| **送信アプリ（4000x3000 の写真）** | **471 MB** | **159 MB**（実測） | 読みながら縮めて、元画像を double 配列で丸ごと持たない |
| 送信アプリ（960px の画像） | 150 MB | 100 MB 前後 | 作業用の配列を float にする |
| **アプリで画像を次々に読む** | **1,004 MB まで増え続ける** | **400 MB で頭打ち** | 1 枚変換し終えたら回収を促す（§4） |

**アバター側は ARGB32 にするだけで半分になる。** これが一番効く。

## 1. アバター側（VRAM）[実測: 計算]

デコーダーは**アトラスを 2 枚**持つ（カメラループは読みながら書けないので、交互に使う）。
テクセルは ARGBHalf = 8 バイト。

| 形式 | アトラス 1 枚 | 合計（2 枚） | うちキャンバス | うち置き場・制御 |
|---|---|---:|---:|---:|
| 3 / 4 | 1024x536 | **8.38 MB** | 8.00 MB | 0.38 MB |
| 5 | 1024x538 | 8.41 MB | 8.00 MB | 0.41 MB |
| 6 | 2048x1044 | 32.63 MB | 32.00 MB | 0.63 MB |
| 10（QR 専用） | 64x58 | 0.06 MB | — | — |

**95% がキャンバス**（描き直し中の作業用と、表示中の完成版の 2 面）。置き場と制御行は誤差。

### 案 A: ARGBHalf → ARGB32（**勧める**）

8 バイト/テクセルが 4 バイトになるので**ちょうど半分**。

置き場に入るのは 0..255 のバイトで、8 bit なら**そのまま正確に入る**（丸め無し）。
制御行の値も全部 255 以下。問題はキャンバスで、**バッチごとに 8 bit に丸められる**こと。

誤差を見積もった [実測: 2 万回の試行]。最悪の想定として「図形 1 個ごとに丸める」でも:

| | |
|---|---:|
| 最終的な誤差の平均 | **0.25 階調**（0..255） |
| 途中も含めた最大誤差 | **1.75 階調** |

**α 合成は前の誤差を (1-α) 倍に減らすので、誤差は溜まらない。** 表示はどのみち 8 bit なので、
見た目に影響しない [推測]。実装したら Unity の試験（期待値との maxdiff）で確かめられる。

### 案 B: 作業用キャンバスをやめる

キャンバスが 1 面になるのでさらに半分。ただし**描き直しの途中が見えてしまう**
（粗い絵 → 細かい絵、を 1 秒ほどかけて繰り返す）。**採らない。**

### 案 C: 制御行の前後の余白を詰める

いまは高さに 16 行の余裕がある（制御行は +8 の 1 行だけ使う）。15 行削れば 0.23 MB。
**ついでにやる価値はあるが、それだけでは効かない。**

## 2. 送信アプリ側（PC の RAM）[実測: ピーク作業セット]

| 画像 | ピーク |
|---|---:|
| 960x640（kodim23） | 150 MB |
| 960x1200（スクリーンショット） | 150 MB |
| **4000x3000（写真）** | **471 MB** |

原因は 2 つ [推測]:

- **元画像を `double[]` で丸ごと持っている**（1 画素 24 バイト）。4000x3000 なら 288 MB。
  形式を変えたときに作り直せるよう、縮める前の画像を保持している
- **符号化の作業用配列**（512x512 の RGB を double で数本、16 スレッド）が 150 MB の土台

減らし方:

1. **読み込みの時点で縮める**。デコードした 8 bit のバイト列から直接 512（または 1024）へ
   縮めれば、288 MB の double 配列を作らずに済む。**ただし縮小の計算順が変わるので、
   出力が今と 1 bit も同じではなくなる**（JS の参照実装との突き合わせが効かなくなる）
2. **保持する元画像を「長辺 2048 まで」に落とす**。4000x3000 なら 288 MB → 75 MB。
   **2048 以下の画像は一切触らないので、参照実装との突き合わせはそのまま効く**
3. **作業用配列を `float` にする**。土台が半分になるが、符号化の結果が変わる

**1 と 3 は出力が変わるので、突き合わせの仕組みを作り直す覚悟が要る。2 は変わらない。**

## 3. 実装（2026-09-18）

**両方入れた。**

### アバター側: アトラスを ARGB32 に

中の値は 0..255 のまま扱い、**読むときに 255 倍、書くときに 255 で割る**ことにした。
シェーダの本体は `Body()` に改名し、`frag` は `Body(i) / 255.0` を返すだけにしてある。
表示シェーダも、255 で割るのをやめた（QR 専用の表示は逆に 255 倍する）。

| 形式 | 前 | 後 |
|---|---:|---:|
| 3 / 4 | 8.38 MB | **4.19 MB** |
| 5 | 8.41 MB | 4.21 MB |
| 6 | 32.63 MB | 16.31 MB |

**画質は変わらなかった** [実測: Unity batchmode]。JS 参照実装との差は **maxdiff 1 のまま**
（ARGBHalf のときと同じ値）。半端パケットを弾く判定・再描画のアイドル判定・図形 1003 個の到達も
すべて前と同じ。QR 専用も 7 項目すべて OK、プレハブ生成 44 項目すべて OK。

### 送信アプリ側: 保持する元画像を長辺 2048 までにする

`ParamroomSession.LimitForMemory`。**2048 以下の画像は触らない**ので、既存の試験・
突き合わせには影響しない。

縮小が 2 段になることによる差を測った [実測]:

| 元画像 | 一発縮小との差（符号化器が見る値） |
|---|---|
| 4000x3000（4:3） | **完全に同一**（0 階調） |
| 4000x2251 | 最大 1.44、平均 0.037 階調 |
| 3841x2161 | 最大 1.37、平均 0.038 階調 |
| 2600x1733 | 最大 2.00、平均 0.030 階調 |

4:3 でぴったり合うのは、2048 が 512 の 4 倍・1536 が 512 の 3 倍で、面積平均の窓が
きれいに重なるため [推測]。他の比でも差は 2 階調以下で、見た目には出ない。

### 読みながら縮める

最初は「読んでから縮める」で入れたが、それだと**持ち続ける量は減っても、読み込み中の山は減らない**
（縮める前に一度は元の大きさの double 配列を作るため）。そこで
**デコードした 8 bit のバイト列から直接縮める**ようにした（`Img.FromRgbaScaled`）。

`FromRgba`（α を白に合成）と `ResizeArea`（面積平均）を続けたのと**同じ順序で同じ演算**をするので、
**結果は 1 bit も変わらない**。試験で総当たりに突き合わせてある
（`ScaledLoadTests`、4 通りの大きさで全画素が完全一致）。

実際に減った量 [実測: 4000x3000 の写真]:

| | 保持している量 | ピーク作業セット |
|---|---:|---:|
| 縮めずに持つ（前） | 274.7 MB | 359 MB |
| 読んでから縮める | 72.0 MB | 422 MB |
| **読みながら縮める（採用）** | **72.0 MB** | **159 MB** |

**持ち続ける量は 1/4、ピークは 359 MB → 159 MB になった。**

## 4. 画像を次々に読み込むとアプリのメモリが増える件 [実測: 2026-09-18]

実機で「複数の画像を読み込んでいくとメモリ使用量が増えていく」「同じ URL を何度も取り込むと
1200 MB まで上った」という報告。切り分けた。

| 何を測ったか | 結果 |
|---|---|
| Core だけ（UI 抜き、ファイルから 18 枚） | 管理ヒープ **65 MB で一定**、作業セットも 285 MB で頭打ち |
| Core だけ（同じ URL を 10 回、2048x2048 の JPEG） | 管理ヒープ **98 MB で一定**、作業セット 380 MB で頭打ち |
| 画像のデコードだけ（WIC・StbImageSharp を 18 枚） | どちらも**一定**（67 MB） |
| **アプリ（同じ URL を 10 回）** | **355 → 1,004 MB まで増え続ける** |

**漏れてはいない。** Core もデコーダも、掴んだままのものは無い（上の測定はいずれも
`GC.Collect()` を強制してから測っている）。増えていたのは**捨てたはずのゴミが回収されていない**ため。

1 枚変換するたびに、元画像（2048x2048 で 100 MB）・作業用キャンバス・デコードした画素と、
**大きなオブジェクトを数百 MB ぶん確保して捨てる**。.NET は「メモリが足りない」と感じるまで
本気で回収しないので、デスクトップアプリのように余裕がある環境では積み上がったままになる。

### 直し方

**1 枚変換し終えたところで回収を促す**（`MainViewModel.ReleaseAfterEncode`）。
大きなオブジェクトの山も 1 回だけ詰め直す（`LargeObjectHeapCompactionMode.CompactOnce`）。

| 回数 | 直す前 | 直した後 |
|---:|---:|---:|
| 1 | 355 MB | 285 MB |
| 5 | 740 MB | 399 MB |
| 10 | **1,004 MB** | **400 MB** |

**かかる時間は 5〜20 ms** [実測]。変換自体が 2 秒ほどかかるので体感されない。
変換は人が操作したときにしか起きず、そのあとは待ち時間なので、ここで回収してよい。

**割り当てを減らす道もあった**が、そちらは符号化器の作りに手を入れることになる。
実害（メモリが減らない）に対して、回収を促すだけで足りることが測定で分かったので、そうした。
