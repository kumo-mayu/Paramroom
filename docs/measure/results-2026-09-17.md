# 実機測定結果（2026-09-17）

手順: [procedure.md](procedure.md)。生データ・集計: `measure/results/2026-09-17/`（録画の復号 CSV、集計レポート）、送信ログ: `measure/logs/`。録画ファイル自体（各 100MB 超）はリポジトリに含めない。

凡例: **[実測]** 今回の測定値 / **[ユーザー報告]** ユーザーが過去のギミック制作で確認した挙動（今回は未再測定） / **[推測]**

## 1. 測定条件
- 同一 PC 上で VRChat クライアント 2 つ（`launch.exe` 経由、デスクトップモード、`--fps=60`、960×540 ウィンドウ）
  - A（profile0）: 測定アバター（ImagePadMeasure プレハブ、Int×32 = 256bit）を着用、OSC 有効
  - B（profile1）: A とフレンド
- 同一インスタンス（Invite）、受信者 1 人、同一ネットワーク
- OSC 送信: 同 PC から `measure/osc/sender.js`、OBS で A・B のウィンドウを 1 画面に並べて 60fps 録画し、`measure/analysis/` で復号・集計
- 注意: 1 回目の録画（13-56-05）は旧プレハブ（値 0 のバイトが前の値のまま残る不具合）のため不採用。修正後の 3 本（rec2〜rec4）を採用

## 2. 結果

### 2.1 値の受け渡し（Int → FX Direct ブレンドツリー → マテリアルプロパティ） [実測]
- **値 0〜255 は受信側・送信側とも厳密な整数で届いた**（厳密値 NG フレーム: rec2 で 0 / 23,684、rec3 で 0 / 13,437）。
- **不具合と修正**: 旧構成では、値が 0 のパラメータに対応するプロパティが書き換わらず前の値が残った（VRChat 上でのみ発生、素の Unity の Animator では再現せず）。常に重み 1 で「全プロパティ = 0」を書く子をブレンドツリーに追加して解消（修正後は 0 を含むパケットも完全一致）。
- rec4 で 76 フレームの厳密値 NG があったが、非表示・再読み込み前後の過渡時に限られる（要確認）。

### 2.2 保持時間と欠落・更新間隔・遅延（T2、1 メッセージずつ送信、rec2） [実測]

| 保持時間 | 受信側の欠落率 | 受信側で新しい値が見える間隔 中央値 / 90% | 送信者自身の表示からの遅延 中央値 / 90% | 受信側の半端パケット |
|---:|---:|---|---|---:|
| 80 ms | **11.4%** | 83 / 100 ms | 100 / 133 ms | 8 / 149 |
| 100 ms | **0.0%** | 83 / 167 ms | 117 / 150 ms | 1 / 149 |
| 117 ms | 0.0% | 100 / 183 ms | 100 / 150 ms | 10 / 149 |
| 133 ms | 0.0% | 150 / 183 ms | 100 / 150 ms | 9 / 149 |
| 150 ms | 0.0% | 167 / 183 ms | 100 / 150 ms | 10 / 149 |
| 200 ms | 2.0% | 183 / 250 ms | 117 / 150 ms | 14 / 149 |
| 300 ms | 0.0% | 317 / 350 ms | 117 / 133 ms | 14 / 149 |
| 500 ms | 0.0% | 500 / 533 ms | 133 / 150 ms | 7 / 149 |

- 保持 80ms のとき（同期の取得間隔が観測値を支配する）、受信側の更新間隔は 3〜7 フレーム（50〜117ms）に分布し、5 フレーム（83ms）が最多。
- 更新間隔の分布の裾に 633 / 750 / 967ms の長い間隔が各 1 回（稀な停止）。200ms の 2% 欠落もこの種の停止と推測。
- 値 500ms（T1、240 パケット）: 欠落 0.4%、受信側の半端パケット 0。

### 2.3 半端パケット（非 atomic な書き込み） [実測]

| 送り方 | 保持時間 | 送信数 | 受信側の欠落率 | 受信側で半端パケットが見えた回数 |
|---|---:|---:|---:|---:|
| 1 メッセージずつ（T2 の 100〜500ms 平均） | 100〜500 ms | 1,043 | 〜0% | 65（**約 6.2%**） |
| **OSC バンドル**（T3） | 100 ms | 299 | 0.0% | 3（**1.0%**） |
| **OSC バンドル**（T3） | 150 ms | 299 | 0.0% | 1（**0.3%**） |
| 1 メッセージずつ＋メッセージ間 2ms 遅延（T4、書き込み約 64ms） | 150 ms | 400 | 1.7% | 315（**79%**） |

- 受信側の半端パケットは 1 回あたり中央値 5 フレーム（約 83ms、次の同期まで）表示される。
- **送信側で 32 個の書き込みが終わる前に同期が値を取得すると、その半端な状態が受信側に届く**、という解釈と整合（書き込み時間を延ばすと急増、バンドルで激減）。
- 送信者自身の表示でも、パケット切り替え時の約 3 割で 1 フレームだけ不整合（OSC の反映がフレームをまたぐ）。

### 2.4 途中参加・非表示・視線外（T5/T6、rec4、保持 150ms・1 メッセージずつ） [実測]

| 操作（推定） | 非表示の長さ | 再表示直後の表示 | 最新に追いつくまで | カメラループのカウンタ |
|---|---|---|---|---|
| ワールド退出 → 再参加（3 回） | 43〜80 秒 | 最新パケット（遅れ 0〜1 パケット） | 0〜50 ms | **0 に戻る**（アバター再読み込み） |
| 後ろを向く → 向き直る（3 回） | 10〜18 秒 | 最新パケット | 17〜500 ms | **増え続ける**（見ていない間もループ継続） |
| Hide Avatar → Show Avatar（2 回） | 22〜29 秒 | 最新パケット（数フレーム不整合） | 50〜150 ms | **0 に戻る**（アバター再読み込み） |

- **途中参加者には現在のパラメータ値が即座に届く**（変化を待つ必要はない）。
- **アバターが再読み込みされると RenderTexture の状態は失われる**（再参加・Show Avatar）。
- **視線を外しただけではカメラループ（と、それを駆動する描画）は止まらない**。スタッフ発言「Animator の停止は距離・表示人数による非表示時のみ」と整合。
- 再表示直後に全ゼロ表示が 1〜9 フレーム出ることがある → **エポック 0 を無効として扱う設計が必要**。
- 各操作の時刻は記録しておらず、非表示区間の長さとカウンタの挙動から操作を推定した（表の「操作」は推定）。詳細: `measure/results/2026-09-17/rec4.events.md`。

### 2.5 可視条件
- **フレンド（B）: カメラループは受信側で動作** [実測]（全録画を通じてカウンタ増加、IsOnFriendsList=1）。
- **非フレンド: Camera コンポーネントがそもそも有効化されない。VRChat 内のセーフティ設定によりシェーダーも無効化されることがある。Show Avatar を押すとそれらの制限はなくなり、フレンド同等、セーフティ設定によってはそれ以上に制限がなくなる** [ユーザー報告]。公式資料（01 報告書 §5.1）とも整合。今回は再測定していない（T7 は未実施）。

## 3. シミュレーションのチャネル仮説との比較

| 項目 | 仮説（docs/design/02 §1.1） | 実測 |
|---|---|---|
| 同期の取得間隔 | 100〜180ms 一様 | 約 70〜110ms（更新間隔の最多 83ms）、稀に 0.6〜1 秒の停止 |
| 欠落率 | 保持 0.14 秒で 7%、0.12 秒で 16% | 保持 100ms 以上でほぼ 0%、80ms で 11% |
| 半端パケット | 5% | 1 メッセージずつ約 6%、バンドル約 0.7% |
| 遅延 | 150ms 固定 | 100〜130ms |
| カリング | ON 30 秒 / OFF 4 秒で受信停止 | 視線外では停止しない。再読み込み（再参加・Show）で状態リセット |
| 途中参加 | 参加後に受信 | 現在値が即座に届く（状態は空から） |

## 4. 限界（未測定）
- VR（90fps 以上）や低フレームレート時の同期間隔
- 受信者が複数・遠距離回線・混雑インスタンス
- 長時間（30 分以上）の安定性
- 非フレンド＋Show Avatar、セーフティ設定ごとの挙動（ユーザー報告のみ）
- Quest 受信（仕様上カメラ・カスタムシェーダー不可）
