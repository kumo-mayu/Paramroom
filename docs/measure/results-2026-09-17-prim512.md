## 512 / 2000（ImagePadPrimDecoder512n2000）

### 条件 [実測条件]

- **録画**：`2026-09-17 17-40-52.mp4`（4:46）
- **送信**
  - コマンド：`node measure/osc/send-image.js sim/images/src/screenshot_mahara.png --R 512 --n 2000 --epoch 3 --duration 240`
  - エンコード：16.5 秒、501 ユニット、縦横比コード 139（1.128）。
- **視聴**：B（フレンド）は約 160 秒時点でワールドに入り直した。
- **画像**：`measure/results/2026-09-17/prim512/`

### 結果 [実測]

- **立ち上がり**（p512-start.png、0.5 秒刻み）
  - 25.0 秒まで表示板は黒（アバター読み込み直後の初期状態）。
  - 25.5〜26.0 秒に灰色（エポック 3 でのリセット）。
  - 26.5 秒に最初の図形が出た。
  - 27.5 秒には、ページの白地・緑の丸 3 つ・右側の緑のボタンの配置が分かった。
  - 送信開始の推定は動画時刻 25.4〜25.6 秒（開始ログ＋エンコード時間）で、到着から約 1〜2 秒で構図が見えた。
- **途中参加**（p512-rejoin.png、0.5 秒刻み）：B がワールドに入った後（約 178.5 秒）、約 181.5 秒には部分的な画像、約 182 秒には緑の丸 3 つが見えた。
- **形**：縦横比 1.128 の横長で表示された。
- **文字の読みやすさ**（p512-close-274.png。B が表示板に近づいた状態）
  - 「Share」「Engage」などの大きな文字は読めた。
  - 本文の小さな文字は読めなかった。
  - JS の期待描画（mahara-js-512n2000.png）でも、本文はほぼ読めない。
- **考察** [推論]
  - 今回はページ全体（960×847）を 512 に縮めたので、本文の文字は元の約半分（高さ 6〜7 px）になり、512 に縮めた時点で読めなくなる。
  - シミュレーションで「読める」と見えた比較画像は、左上 480×480 を切り出したもの（文字は約 2 倍）だった。条件が違う。
  - 図形数やシェーダーの問題ではなく、送る範囲（倍率）で決まっている。
- **FPS**：録画からは読み取れていない。

## 512 / 4000（ImagePadPrimDecoder512）

### 条件 [実測条件]

- **録画**：`2026-09-17 17-50-44.mp4`（7:03）
- **送信**
  - コマンド：`node measure/osc/send-image.js sim/images/src/screenshot_mahara.png --R 512 --n 4000 --epoch 1 --duration 360`
  - エンコード：30.3 秒、1001 ユニット。
- **視聴**：B は約 230 秒時点でワールドに入り直した。

### 結果 [実測]

- **立ち上がり**（p4k-sheet.png、8 秒刻み）
  - 送信開始の推定は動画時刻約 41 秒。40 秒のフレームで粗い構図、48 秒のフレームで緑の丸と右側のボタンが見えた。
  - 2000 版と同じく序盤は速い。シミュレーションの「20 秒までは図形数に依存しない」と整合する。
- **途中参加**：入り直した後、ワールドに入ってから 8 秒以内のフレーム（256 秒）で、構図の分かる画像が出ていた。
- **利用者の感想** [実測・主観]
  - 負荷はそれほど感じない。
  - 細かい字が少し読めるようになった気がする。
- **2000 版との比較（録画）**
  - p2k-vs-4k.png の 2 つの録画は視点の距離が違うので、厳密には比べられない。
  - 4000 版では、太字の行（…day at 8 p.m. (New Zealand). All content will be erased then）や Profile completion tips が読めた。
- **2000 版との比較（JS 期待描画、同じ切り出しを 2 倍に拡大、mahara-src-2k-4k.png）**
  - 2000 版：本文はほぼ読めない。
  - 4000 版：本文の多くの語が読める（Mahara is a fully featured web application to build your electronic portfolio など）。
  - 利用者の感想と整合する。

### エンコード時間（1024 キャンバスの見積もり用）[実測]

計測時は、他のエンコードや動画解析と同時に動いていたので、実際より遅めの値である。

| キャンバス / 図形数 | 時間 |
|---|---|
| 512 / 2000 | 14.1 s（単体） |
| 512 / 4000 | 27.9 s（単体）、30.3 s（送信時） |
| 1024 / 1000 | 36.9 s（座標 9 bit）、37.6 s（座標 10 bit） |
| 1024 / 2000 | 56.1 s |

- 1024 では図形 1 個あたり約 19 ms で、512 の約 7 ms の約 2.7 倍。
- 固定分（約 18 s）を足すと、1024 / 4000 は約 1.5 分、8000 は約 3 分、16000 は約 5.5 分と見積もられる [推論]。

## C# センダー（tools/ImagePadTool）での 512 / 4000

### 条件 [実測条件]

- **録画**：`2026-09-17 18-59-26.mp4`（5:38）
- **送信**（ログ `measure/logs/cs/cs-send.log`）
  - kodim23（事前にエンコード済み、`--units`）を epoch 2 で 150 秒送った。
  - 続けて screenshot_wikipedia を、その場でエンコード（2.14 秒）して epoch 3 で 150 秒送った。
  - 宛先はどちらも OSCQuery で自動選択した。見つかったクライアントは 2 つ（OSC 9000 と 9010）で、D0..D31 を持つ 9000 側だけが選ばれた。
- **画像**：`measure/results/2026-09-17/cs/`

### 結果 [実測]

- **切り替え**：どちらの切り替えでも、リセット（背景色）の後に新しい画像が描かれた。縦横比も正しかった（横長 1.50 → 縦長 0.54、cs-sheet.png、cs-wiki320.png）。
- **送信開始の遅れ**：OSCQuery による探索の待ち時間（既定 3 秒）の分だけ、送信開始が遅れる。1 回目のリセットは動画時刻約 15.3 秒で、ログの開始（12.6 秒）＋探索 3 秒と整合する（cs-sw1.png）。
- **JS センダーとの違い**：体感できる違いはなかった。送信内容・間隔・送信順は、ローカルの検証で JS 版と一致を確認済み（tools/ImagePadTool/README.md）。
