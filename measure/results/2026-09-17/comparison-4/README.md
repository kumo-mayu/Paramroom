# 実用候補 4 構成の比較（512/2000、512/4000、1024/2000、1024/4000）

比較画像は `sim/make-comparison.js sheets <dir> 512/2000,512/4000,1024/2000,1024/4000` で作成した。どれも全ユニットが揃った状態の描画。

- **overview**：全体を長辺 480px に縮小したもの。
- **zoom**：長辺 1024px 表示の一部を等倍で切り出したもの。

写真 kodim23 は元画像が 512px なので、1024 構成の利点は出ない。

## 全ユニット揃った時の画質 [シミュレーション]

MS-SSIM (YCbCr 6:1:1) / PSNR。元画像を同じサイズに縮小・拡大したものと比べた。

| 画像（比較サイズ） | 512/2000 | 512/4000 | 1024/2000 | 1024/4000 |
|---|---|---|---|---|
| Mahara ページ全体（1024） | 0.950 / 25.1 dB | 0.968 / 26.1 dB | 0.957 / 25.8 dB | **0.973 / 27.6 dB** |
| Mahara ページ全体（512） | 0.977 / 27.4 dB | **0.988 / 29.6 dB** | 0.979 / 28.0 dB | 0.987 / 30.2 dB |
| イラスト（1024） | 0.985 / 31.6 dB | 0.992 / 33.0 dB | 0.990 / 33.7 dB | **0.995 / 37.3 dB** |
| 写真 kodim23（512） | 0.967 / 31.7 dB | 0.981 / 34.2 dB | 0.970 / 31.9 dB | **0.983 / 33.8 dB** |

見た目（zoom）での文字の読みやすさ：

| 構成 | Mahara 本文 |
|---|---|
| 512/2000 | ほぼ読めない |
| 1024/2000 | 太字は読めるが、本文は所々だけ |
| 512/4000 | 大部分が読める |
| 1024/4000 | ほぼ元画像並み |

## デコーダーの負荷・実装 [推論、512 は Unity/VRChat で実測]

| 項目 | 512 | 1024 |
|---|---|---|
| アトラス（ARGBHalf、2 枚） | 1024×536、約 8.6 MB | 2048×1040、約 34 MB |
| 描き直し中の 1 パスの画素数 | 基準 | 4 倍 |
| 描き直し 1 周の時間（32 図形/パス、2 パス/フレーム、60 fps） | 2000：約 0.5 s、4000：約 1 s | 同じ（負荷を抑えるためにパスあたりの図形数を減らすと、その分長くなる） |
| 図形の保存領域（8192 テクセル） | 4096 個まで | 4096 個まで（幅 2048 × 4 行） |
| 座標のビット数 | 9 bit（1 px 刻み） | 10 bit（9 bit だと 2 px 刻み） |
| 縦横比バイト（毎パケットの空き） | 入る（空き 12〜13 bit） | 入らない（空き 4〜6 bit）→ unit 0 などに移す必要がある |
| 実装状況 | 済み | シェーダーは `_Canvas=1024` と座標 10 bit への対応が必要 |

## まとめ [推論]

- **1024/2000 は 512/4000 に劣る**。画質（Mahara 1024 比較：0.957 対 0.968、文字の読みやすさ）、エンコード時間、描画負荷、VRAM のいずれでも 512/4000 の方がよく、送信時間の差は 50 s 対 100 s だけ。
- **512/4000**：実装済み・実機確認済み。本文の文字も大部分読める。現時点で最もバランスがよい。
- **512/2000**：全部揃うまでが半分で、途中参加の序盤も少し速い。文字を読む必要がない用途（写真・イラスト）なら十分。
- **1024/4000**：文字は最も読みやすい。一方で VRAM 4 倍、描画負荷 4 倍、エンコード数分、縦横比バイトの置き場所の変更が必要。細かい文字が主な用途なら検討の価値がある。
