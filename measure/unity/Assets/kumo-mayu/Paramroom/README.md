# Paramroom（アバターに入れる部品）

VRChat の同期パラメータ（Int）だけを使って、静止画を周りの人に送るための受信側です。送信は PC 側のアプリ（`tools/Paramroom.App`）が行います。

## 先に知っておくこと（導入できるかの条件）

- **相手からは、フレンドか「Show Avatar」を押した人にしか見えません**。アバター上の Camera がリモートで動く条件がそれだからです（`docs/research/01-vrchat-parameters.md`）。
- **Android 版（Quest 単機など）・iOS 版では動きません**。Camera もカスタムシェーダーも無効になります。PC 版専用です。
- **同期パラメータを最大 32 Int（256 bit）使います**。アバターの空きビット数に収まる Int 数を選んでください（ビルダーがアバターの空きを表示します）。
- **アバターを読み込み直されると絵は消えます**（相手が再参加した、Show Avatar を押し直した等）。送り続けていれば 1 周で戻ります。
- **相手がこちらを「遠すぎる」「表示人数制限」で隠している間は、絵が進みません**。表示に戻ると読み込み直しになるので、
  そこから 10〜20 秒で見られる程度に戻り、1 周（形式 4 ＋ 32 Int で 80 秒）でほぼ揃います（全部揃うまでは 90 秒ほど）。
  人の多いワールドでは、**見せたい相手に近づいてもらう**のが確実です。
- **同じアバター（同じ blueprint ID）を 2 人以上が着ていると、絵が壊れます**。カメラループの RenderTexture をアバター ID 単位で共有してしまうためです（VRChat 側の仕様）。配布アバターにそのまま入れる場合は、着る人ごとに別アップロードが必要です。
- シェーダーを許可していない相手（セーフティ）には、表示板ごと見えません。

### 利用上の注意

送信する画像について、必要な著作権その他の権利・許諾を確認して使用してください。第三者の権利を侵害する画像や、
VRChat の [Terms of Service](https://hello.vrchat.com/legal) / [Community Guidelines](https://hello.vrchat.com/community-guidelines) /
[Creator Guidelines](https://hello.vrchat.com/creator-guidelines) に反するコンテンツの送信には使用しないでください。

## 送れるもの：画像と QR コード

**どの形式のプレハブでも、画像と QR コードの両方を出せます**。どちらを出すかは送信アプリ側で決めるので、
プレハブを作り直す必要はありません。

| | 画像 | QR コード |
|---|---|---|
| 揃うまでの時間 | 80 秒ほどでほぼ揃う（全部は 90 秒ほど。形式 4 ＋ 32 Int。10〜20 秒でだいたい分かる絵になる） | **1 秒かからない**（32 Int。例: 25×25 升で 3 パケット = 0.3 秒） |
| 用途 | 写真・イラスト・資料 | URL などの文字列 |
| 相手が隠していた場合 | 表示に戻ってから 1 周（80 秒）でほぼ戻る | 表示に戻ってすぐ |

QR コードは、白黒の升目そのものをパケットに載せています（画像として送ると 12〜27 秒かかりますが、
升目として送れば 0.3 秒で済みます。`docs/research/09-qr-code.md`）。

## 作れる形式

図形 1 個のビット数：形式 3 は 58 bit、軽量（形式 4/5）は 47 bit（座標 8・半径 6・角度 5・色 444・α 2）、形式 6 は 59 bit。

| `Paramroom_Format` | 内容 | 選べる Int の数（1 周の時間、100 ms/パケット） |
|---|---|---|
| **4** | **512px・図形 4000 個・軽量（これを使う）** | 9（400 s）/ 15（200 s）/ 21（133 s）/ 26（100 s）/ **32（80 s）** |
| 3 | 512px・図形 4000 個・精度高め | 10（400 s）/ 18（200 s）/ 25（133 s）/ 32（100 s） |
| 5 | 512px・図形 5000 個・軽量 | 9（500 s）/ 15（250 s）/ 21（167 s）/ 27（125 s）/ 32（100 s） |
| 6 | 1024px・図形 4000 個（**実験用**。下の注意を読むこと） | 11（400 s）/ 18（200 s）/ 25（133 s）/ 32（100 s） |
| **10** | **QR 専用**（画像は出せない。ビルダーの「QR 専用」タブ） | 3〜16（短い URL で 3.2 s〜0.4 s） |

- **迷ったら形式 4 ＋ 32 Int**（ビルダーも最初からこれを選んでいます）。1 周 80 秒で、10〜20 秒でだいたい分かる絵になります。
- **「1 周」は全パケットを 1 回ずつ送る時間**です。1 周でほぼ揃いますが、全部揃うのは 1 周の 1.15 倍ほど
  （送信アプリが 8 回に 1 回を重要な図形の再送に回すため。形式 4 ＋ 32 Int で 90 秒ほど）。
- **形式 10（QR 専用）**は、同期パラメータがほとんど空いていないアバター向けです。画像用の
  割り付け（1 パケットに図形 1 個）を使わないので **Int 3 個**から動き、4 Int で短い URL が 2.0 秒。
  表示板も 512x512 のキャンバスを持たず、升目ぶんのテクセルだけになります
  （`docs/research/09-qr-code.md` §6）。出せるのは 57x57（版 10）までです。
- 軽量（4/5）は序盤の見え方が少し速い代わりに、線画や文字の最終的な画質がわずかに落ちます。
  形式 3 はその逆で、最終画質がわずかに上、1 周 100 秒・下限 10 Int です。
- **Int の下限**：画像も出すなら形式 4/5 の 9 Int（72 bit）、QR だけなら形式 10 の 3 Int（24 bit）。
- **形式 1（256/1000）と 2（512/2000）**：もう作りません（2026-09-17）。既にそれを入れたアバターには送信側からそのまま送れます。
- 形式の比較：`measure/results/2026-09-17/precision`、`comparison-4`、`measure/results/2026-09-18/repr`。

## 入れかた

1. この `Paramroom` フォルダを、`kumo-mayu` ごとアバターのプロジェクトの `Assets/` に入れる（`Assets/kumo-mayu/Paramroom` になります）。
2. ヒエラルキーでアバター（またはその子）を選ぶ。ビルダーが空きビット数を表示します。
3. **Tools/Paramroom/Decoder Builder** を開き、形式と Int の数を選んで作る。
4. できた `Assets/kumo-mayu/Paramroom/ParamroomDecoder*.prefab` をアバターの直下に置く。
5. 表示板（`Display`）を見せたい位置・大きさに動かす。
6. アバターをアップロードする。
7. PC 側で送信アプリを起動すると、アバターを自動で見つけて送り始めます。

## 中身

| 場所 | 中身 |
|---|---|
| `Editor/ParamroomBuilder.cs` | **Tools/Paramroom/Decoder Builder** のウィンドウ。形式と Int の数を選び、`Assets/kumo-mayu/Paramroom/ParamroomDecoder*.prefab` を作る |
| `Editor/ParamroomModularAvatar.cs` | Modular Avatar のコンポーネントを付ける共通の処理（測定用のビルダーも使う） |
| `Shaders/ParamroomDecoder.shader` | カメラループで図形を描き直すデコーダー |
| `Shaders/ParamroomDisplay.shader` | 表示板（縦横比に合わせて形を変える） |

プレハブは Modular Avatar の Merge Animator と Parameters を使います。同期パラメータは `Paramroom_D0`..`Paramroom_D(n-1)`（Int）、それに加えて `Paramroom_Format`（**同期しない**ローカル専用の Int。送信側が形式を知るために使う）を登録します。

- 名前に `Paramroom_` を付けているのは、他のギミックとの衝突を避けるためです（パラメータ名は同期されないので、長くても 256 bit の枠は使いません）。
- **2026-09-18 より前に作ったプレハブは `D0`.. という名前**です。送信アプリは両方を自動で判別するので、そのままでも送れます。
- Write Defaults は ON で作ります（単一レイヤーの Direct Blend Tree のため）。アバター全体を OFF で統一している場合は VRChat の警告が出ます。

## 形式 6（1024px）についての注意

1024 は「近づいて見たときに文字が読めるか」を上げるための候補ですが、**VRChat での負荷を測るために用意したもので、採用は決めていません**（`docs/research/08-primitive-representation-experiments.md` §17）。通常は形式 4 を選んでください。

- 図形 1 個は **59 bit**（座標 10・半径 8・**角度 5**・色 565・α 2）。座標に 10 bit 要るので角度を 1 bit 削り、パケットに縦横比コード用の 8 bit を残している
- **アトラスが 2048x1044 になる**（512 のときは 1024x536）。ARGBHalf なので **1 枚 16.3 MB、2 枚で約 33 MB の VRAM**（512 は合計 9 MB）。VRChat の Texture Memory の評価に算入される場合、ランクが下がる可能性があります（未確認）
- **1 パス（= 1 フレーム）の画素数が約 4 倍**になる。1 周（4000 図形）に要するパス数は 512 と同じ 126 なので、**フレーム当たりの負荷が約 4 倍**という見積もり
- シミュレーション上は、**元画像を大きく縮小して送る場合（ページ全体のスクリーンショットなど）にしか利点がありません**。切り出した画像では 512 のほうが良い結果でした
- 重すぎる場合は、ビルダーの `Format.batch`（1 パスで描く図形数、既定 32）を下げてから作り直すと、フレーム当たりが軽くなる代わりに 1 周のフレーム数が増えます。**生成済みのマテリアルを手で書き換えるときは A/B 両方を同じ値にしてください**（食い違うと絵が完成しません）

## 測定用の道具との分け方

同期の遅れや取りこぼしを測る表示板とそのビルダー、デコーダーの自動テスト（`ParamroomShaderTest`）とテストデータは `Assets/ParamroomMeasure` に置いています。アバターに入れるのは `Assets/kumo-mayu/Paramroom` だけでよいです。

## 前の配置（Assets/ParamroomMeasure に全部あった版）から移すとき

1. アバターのプロジェクトの `Assets/ParamroomMeasure` から、`Editor/ParamroomBuilder.cs`、`Shaders/ParamroomDecoder.shader`、`Shaders/ParamroomDisplay.shader` を消す。残すと同じクラスやシェーダーが 2 つになり、コンパイルエラーやシェーダーの取り違えが起きる。
2. この `Paramroom` フォルダを `Assets/kumo-mayu/Paramroom` として入れる。
3. ビルダーでプレハブを作り直し、アバターの古い `ParamroomDecoder*` と入れ替える。古いプレハブと `GeneratedPrim*` フォルダは、消したシェーダーを指しているので消してよい。
