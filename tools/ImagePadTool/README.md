# imagepad（C# エンコーダー＋センダー）

prim デコーダー（512/4000 など）向けの、エンコーダーと OSC センダーの C# (.NET 9) 実装。
`measure/osc/send-image.js`（JS 版）と同じワイヤ形式を使う。送信順の既定は `fast+sqrt/8`（2026-09-17 に決定。JS 版の既定は平方根則のまま）。

## ビルド

```
cd tools/ImagePadTool
dotnet build -c Release
# 実行ファイル: bin/Release/net9.0/imagepad.exe
```

## 使い方

```
imagepad list                                   # OSCQuery で見つかった VRChat クライアントと、ImagePad パラメータの有無
imagepad send <画像> [--R 512 --n 4000]          # エンコードして送信（既定 512/4000、画像全体を引き伸ばし＋縦横比）
imagepad send <画像> --epoch 2 --duration 300    # 画像を切り替えるときは epoch を変える（1〜3）
imagepad encode <画像> --out units.json --png canvas.png   # エンコードだけ（結果の保存と確認用 PNG）
imagepad send --units units.json                # 保存したエンコード結果を送信
```

- **送信先の決め方**
  - 既定では vrc-oscquery-lib（VRChat 公式のコミュニティライブラリ）で VRChat クライアントを探す。
  - 現在のアバターに Int パラメータ D0..D31 があるクライアントに送る。
  - 該当が複数あるときは `--client <名前の一部 | OSC ポート>` で選ぶ。
  - `--port`（と `--host`）を付けると、OSCQuery を使わず固定の宛先に送る。
- **Int パラメータの数（汎用版、2026-09-17）**
  - プレハブは Unity の **Tools/ImagePad/Prim Decoder Builder** で作る。フォーマット（256/1000、512/2000、512/4000）と Int の数を選ぶ。
  - Int の数は、1 パケットの図形数が変わる境目だけを選べる。

    | フォーマット | Int 10 | Int 17 / 18 | Int 25 | Int 32 |
    |---|---|---|---|---|
    | 256/1000 | 1 個/パケット、1 周 100 s | 17 Int：2 個、50 s | 3 個、33 s | 4 個、25 s |
    | 512/2000 | 1 個、200 s | 17 Int：2 個、100 s | 3 個、67 s | 4 個、50 s |
    | 512/4000 | 1 個、400 s | 18 Int：2 個、200 s | 3 個、133 s | 4 個、100 s |

  - 選んだアバターの「他のギミックの同期ビット数」は、NDMF の ParameterInfo（Modular Avatar の Parameter Usage ウィンドウと同じ情報源）で表示し、空きに収まる数だけを選択可能にする。
  - センダーは OSCQuery で D0.. の個数を数え、パケットの大きさとユニットの割り付けを自動で合わせる。
- **軽量の形式（2026-09-17）**：`ImagePad_Format` 4 = 512px・図形 4000 個、5 = 512px・図形 5000 個。図形 1 個 47 bit（座標 8・半径 6・角度 5・色 444・α 2）。
  - 比較の結果：measure/results/2026-09-17/precision。見た目は標準（58 bit）とほぼ同じ。
  - 選べる Int の数：9 / 15 / 21 / 26 / 32。形式 5 は 27 が 26 の代わり。
  - 形式 4 で Int 26 個にすると、標準形式の Int 32 個と同じ 1 周 100 秒になる。
  - 形式 4 で Int 32 個にすると、1 パケットに 5 個入り、1 周 80 秒。
  - 形式 5 は図形が 4096 個を超えるので、アバター側の図形の保存領域を広げてある（プレハブのビルダーが自動で設定）。
- **図形数の変更**：同じフォーマット（同じキャンバス）なら、デコーダーの上限より少ない図形数（`--n 2000` など）で送れる。割り付けは同じで、ユニット数が減るだけ。デコーダーは届かない図形を描かない。
- **デコーダーの種類の自動判定**
  - プレハブには、同期しない Int パラメータ `ImagePad_Format` が入っている（1 = 256/1000、2 = 512/2000、3 = 512/4000。同期しないので 256 bit の枠は使わない）。
  - センダーは OSCQuery でこの値を読み、`--R` / `--n` を自動で決める。
  - `--R` / `--n` や `--units` のデータがアバターの種類と合わないときは送らない（`--force` で強制）。
  - 値が読めないとき（このパラメータを持たない旧プレハブ、`--port` 指定時）は、指定値か既定の 512/4000 を使う。
  - `encode` では `--format 1|2|3` でも指定できる。
  - プレハブへの追加は Unity のバッチ生成で確認済み。VRChat 上で値が読めるかは未確認（アバターの再アップロードが必要）。
  - OSCQuery から同期パラメータの現在値が読めることは実機で確認した（D0 = 207）。
- **送信順（`--schedule`）**
  - `fast+sqrt/8`（既定）：1 周目は全ユニットを重要な順に送りつつ、8 スロットに 1 回を平方根則に回す。1 周目が終わったら平方根則に切り替える。0.90 に届くまでの秒数（512/4000、16 枚平均）は、開始時から見ている人で 14 秒（sqrt 17 秒、fast 12 秒）、1 周目の最中に参加した人で 39 秒（sqrt 27 秒、fast 95 秒）。
  - `sqrt`：最初から平方根則で送る。途中参加に最も強い。
  - `fast`：1 周目は全ユニットを重要な順に 1 回ずつ送り、2 周目から平方根則に切り替える。開始時から見ている人には速い（512/4000 で 5 s：0.842 対 0.818、60 s：0.965 対 0.952）。ただし 1 周目（約 100 s）の途中に入った人には大きく遅れる（5 s：0.478 対 0.729）。`sim/results/fastfirst.md`
  - `fast+sqrt/k`、`fast+sqrtB/k`、`fast+baseB/k`：fast の 1 周目の k スロットに 1 回、平方根則（先頭 B ユニットに限定も可）や先頭 B ユニットの再送を挟み、途中参加の人にも粗い像を早く出す。例：`--schedule fast+sqrt32/8`。比較は `measure/results/2026-09-17/fastfirst/README.md`。
  - `carousel`：巡回のみ。
- **その他のオプション**
  - `--fit crop`：中央を正方形に切り出す。
  - `--hold`：パケット間隔（ms、既定 100）。
  - `--no-bundle`：OSC バンドルを使わず、1 メッセージずつ送る。
  - `--seed`：エンコーダーの乱数シード。

## 検証 [実測、2026-09-17、Ryzen 7 5800X3D]

| 項目 | 結果 |
|---|---|
| ワイヤ形式 | C# の出力ユニットを JS デコーダー（sim/codecs/prim.js）で描画すると、C# エンコーダーの内部キャンバスと完全一致（最大差 0）。`sim/verify-cs.js` |
| 画質（テスト 16 枚、512/4000、512 参照 MS-SSIM / PSNR） | C# 0.9773 / 32.68 dB、JS 0.9768 / 32.60 dB。全 16 枚で C# が同等以上（`verify-512-4000.txt`） |
| エンコード時間（512/4000） | 平均 2.26 s（JS：単体 28 s、14 並列時 63 s） |
| 送信 | 51 バンドルすべてが正しいユニット（エポック・縦横比込み）。間隔の平均 99.99 ms、標準偏差 0.39 ms。送信順は JS の平方根則と一致（`measure/osc/check-sender.js`） |
| OSCQuery | 起動中の 2 クライアントを検出（OSC 9000 / 9010）。ImagePad パラメータのある方（D0..D31 が 32/32）だけを送信先に選んだ |

## 高速化の内容（PrimEncoder.cs）

- **候補の評価**：楕円が各行で覆う画素の区間を解析的に求める。色と α の閉形式の解に必要な和は、行ごとの累積和から得る。これで評価が O(画素数) から O(行数) になった。
- **探索の解像度**：JS 版の「2 画素おきの粗探索」をやめ、常に全解像度で正確に評価する。そのため画質はむしろ少し上がった。
- **区間の端**：探索中は解析解だけを使う。採用した図形は、デコーダーと同じ画素中心判定で再評価する。
- **更新範囲**：誤差マップと累積和は、描いた図形が通る行だけを更新する。候補画素のサンプリングは、行の累積和上の二分探索で行う。
- **並列化**：乱択候補の評価と山登り 4 本を並列に実行する。山登りはそれぞれ専用のシード付き乱数を使うので、結果はスレッド数によらず決定的。
- **スレッド数と時間**：1 スレッドで約 5 s、4 スレッド以上で約 2.3〜3 s。山登り 4 本が律速なので、それ以上のスレッドでは速くならない。
